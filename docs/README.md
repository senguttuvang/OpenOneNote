# O2N Design And Product Notes

These articles explain the engineering and product choices behind O2N: customizing a familiar notebook client, preserving collaboration with official OneNote and deciding how much infrastructure a team should own.

- **[Building a compatible OneNote client](compatible-onenote-client.md):** Markdown versus rendered content, the system of record, source recovery, annotations and possible shared-metadata designs.
- **[Custom software and the SaaS trade-off](custom-software-and-saas.md):** useful feature subsets, build-versus-buy economics and the operating work that remains after a fast prototype.
- **[Product roadmap](../ROADMAP.md):** the tested baseline, near-term hardening, planned editing/review features and exploratory directions.

The articles develop the reasoning behind the project; proposed extensions are not announcements of shipped features. For implementation contracts, read the [native-shell specification](../specs/native-shell.md) and [document/sync architecture](../reconstruction/markdown-first-architecture.md). The [dated acceptance record](../reconstruction/oauth-sharepoint-acceptance.md) describes actual interoperability tests. Release contents and license scope are covered in the [release guide](../PUBLIC_RELEASE.md).
